# ADR-001 — Local-first Android beta và quy tắc tuần

Status: **D01 Accepted 05/11/2026; D03 Accepted 06/11/2026**, theo yêu cầu trực tiếp
của chủ sản phẩm. D03 gồm tuần thứ Hai, timezone IANA từ thiết bị được cố định theo
chuỗi, preview đổi zone ở kỳ kế và kỳ chuyển tiếp liền mạch. D04–D13 và transaction/
outbox mới vẫn Proposed; không coi toàn bộ ADR đã Accepted. Xem [D01](d01-local-first.md),
[D03](d03-schedule-timezone.md) và [gate](README.md).

## Lựa chọn lưu trữ

| Tiêu chí | SQLite local-first (D01 đã chọn) | Supabase-authoritative + offline cache |
|---|---|---|
| Nguồn chuẩn core | SQLite trên installation + owner | Server; local pending commands chưa là kết quả chuẩn |
| Offline/guest | Ghi local atomic ngay, guest sẵn có | Cần guest store + command queue, reconciliation lúc login |
| Multi-device | Không hỗ trợ journal sync trong beta | Có thể hỗ trợ, phải xử lý retry/revision/ownership |
| Xung đột | Một DB, transaction + compare-and-swap revision | Server idempotency, optimistic versions, merge/khước từ command |
| Migration hiện hữu | Additive quanh activity_logs v2 | Upload/import, mapping identity, tránh duplicate và rollback import |
| Rủi ro | Uninstall/clear storage có thể làm mất journal, không có backup journal của Steady | Mạng/auth chặn confirmation, sync phức tạp, RLS staging bắt buộc |

Chọn local-first vì mục tiêu Android/offline và nhật ký v2 đã có. Supabase tiếp tục
Auth và các module food/reminder hiện hữu; không thành nguồn chuẩn core chỉ vì
đã có SDK. Analytics sink là bản chiếu đo lường, không dùng khôi phục journal.
Beta yêu cầu một installation cho mỗi participant; ghi rõ giới hạn khi tuyển.
Nếu multi-device/cloud backup là điều kiện bắt buộc, D01 phải đổi trước PR1–2.

Domain thuần Dart không import Flutter/SDK; repository transaction và clock/timezone
adapter được inject. CommitmentController/RecoveryController riêng, SteadyStore
giữ activity/research hiện hữu. Một database transaction bao trùm core + activity
v2 + outbox, không để repository mỗi entity tự commit riêng.

## Identity, persistence và conflict

- Owner local: guest UUID có prefix `guest:` hoặc Supabase user UUID hiện hữu.
  Không thay key của logs cũ. Guest identity tạo trong SQLite transaction hiện có.
- Capture owner + identity generation + expected revision lúc command bắt đầu;
  mỗi query theo owner, FK composite bảo vệ liên kết cùng owner. Stale UI response
  không tác động phiên mới. Đăng nhập không tự gộp guest, không tự upload journal.
- Command ID tạo và persist trước retry; unique `(owner_id, command_id)` trong
  command receipts. Cùng ID/cùng payload trả result cũ; khác payload trả conflict.
  Completion còn bị chặn bằng unique credit root dù hai command ID khác nhau.
- CAS revision trên session/commitment. Reschedule song song completion: một commit
  trước, command sau đọc lại và yêu cầu người dùng sửa; không last-write-wins.
- Không có core sync trong beta. Outbox sync chỉ events với at-least-once transport,
  server dedup event_id. Nếu thêm core sync tương lai: ADR riêng, server receipt +
  revision, replay commands theo owner; không merge tổng progress/denominator.
- Preferences không đủ atomic nhiều entity. Engine mới Android-only cho tới khi
  có adapter transaction tương đương và migration platform riêng được duyệt.

## Ranh giới transaction và side effects

| Command | Một transaction phải commit cùng nhau | Sau commit |
|---|---|---|
| Create/repeat commitment | commitment + target snapshot + initial sessions + receipts + consented outbox | UI success, reconcile reminders |
| Schedule/reschedule | session revision + recovery selection nếu có + receipt + outbox | Cancel/replace lịch native theo revision |
| Complete | ActivityLog + activity metadata + credit allocation + session status + recovery outcome + receipt + outbox | UI progress, cancel reminder |
| Detect missed | CAS trạng thái + missed episode + outbox | Có thể hiển thị prompt; không auto nghỉ/giảm target |
| Rest/correction/undo | audit action + trạng thái/credit cập nhật + revision + outbox | Reconcile reminders, recompute projection |
| Consent revoke | consent generation + xóa queue chưa gửi + deletion request local | Dừng uploader, gửi yêu cầu xóa khi có mạng |

Không gọi plugin/network trong DB transaction. Reminder desired-state được lưu
atomic cùng command, reconciler retry sau crash. View events persist riêng khi
visible thực sự, không phát ở build(). Không consent thì không tạo analytics row;
domain transaction vẫn thành công khi chưa có mạng.

## Quy tắc thời gian và credit (policy_version = 1 dự kiến)

1. **D03 Accepted:** tuần `[Monday 00:00, next Monday 00:00)` theo IANA lấy từ thiết
   bị lúc bắt đầu chuỗi, rồi snapshot cho từng kỳ; không theo timezone máy tức thời
   mỗi lần render. Lưu local label, zone và UTC boundaries, không cộng cứng 168h.
   Khi travel giữ nguyên kỳ hiện tại; preview zone mới và chỉ áp dụng ở kỳ kế.
   Kỳ chuyển tiếp có `start = previous.end`; `end` là thứ Hai 00:00 đầu tiên có UTC
   instant **lớn hơn** start trong zone mới. Không gap/overlap, không kéo dài thêm
   một tuần nếu kỳ chuyển tiếp ngắn. Lưu `period_kind=timezone_transition` và sequence
   thay vì suy ID từ local Monday. Kỳ sau trở lại Monday–Monday. Xem ví dụ và preview
   trong [D03](d03-schedule-timezone.md). Việc loại transition khỏi KPI vẫn là đề xuất
   D13; target/partial/repeat thuộc D04, không được tự prorate từ D03.
2. DST: giờ không tồn tại dịch tới phút hợp lệ đầu tiên và yêu cầu xác nhận;
   giờ trùng chọn offset sớm hơn có preview. Persist offset + UTC, không re-resolve
   lịch cũ khi tz database cập nhật. PR2 cần fixtures DST/travel dù beta ở Việt Nam.
3. Target 1–7 bất biến từ lúc tạo kỳ. Tuần đầu có thể partial, snapshot ngay lúc
   tạo, không prorate. Target edit lưu pending cho kỳ sau. Health rest không đổi
   mẫu số; báo rest riêng và diễn đạt trung tính.
4. Adherence = `min(1, count(valid active credits in commitment) / target_at_start)`.
   Không activeDays/rolling 7 days/targetDays=5/streak. Buổi tự do trong khoảng kỳ
   có thể nhận một credit standalone, không cần có lịch. Logs trước commitment
   hoặc legacy logs không tự nhận credit. Thêm nhiều logs cho cùng buổi không được
   nhiều credit; người dùng xác nhận “buổi khác” cho standalone, không suy từ UUID.
5. Một scheduled session có credit root bất biến; reschedule/short alternative
   không sinh root mới. Threshold thông thường ≥10 phút, short recovery ≥5 phút
   nếu đã chọn trước actual start. Nhiều buổi thực sự khác trong ngày được tính;
   kiểm tra actual start/end không overlap giữa active credited activities cùng
   owner trong transaction; không chia nhỏ một lần tập thành nhiều credit.
6. `completed_at` là kết thúc thực tế, `recorded_at` là lúc nhập, actual start suy
   từ duration; không tương lai. Planned duration không chứng minh completion.
   Completion hợp lệ phải có actual interval nằm trong kỳ được credit; không tự
   chuyển credit giữa tuần. Log vượt boundary vẫn được lưu, không tự split credit.
7. Deadline = planned end + grace 2h, capped tại week end. Missed khi `now >= deadline`
   và chưa có valid completion/rest/cancel. Detect khi mở/resume/sau edit, idempotent
   theo session + schedule revision. `occurred_at` deadline, `detected_at` lúc reconcile.
   Không hứa background detection đúng giây khi app tắt.
8. Late/backdated log tới week end +7 ngày được sửa projection tuần cũ nếu actual
   interval thuộc kỳ đó. Log nhập muộn nhưng tập đúng hạn phải retract missed sai;
   tập sau deadline trong cùng kỳ là late completion và giữ missed occurrence thật.
   Sau cutoff vẫn lưu/correct journal nhưng không rewrite frozen KPI; báo khác biệt.
9. Dời qua tuần: giữ buổi cũ missed/cancelled theo thời điểm, tạo session mới/root mới
   thuộc commitment tuần mới, `carried_from_session_id` để trace, không credit tuần cũ.
   Nếu chưa có commitment mới, người dùng phải tạo/xác nhận trước; không auto target.
10. Rest intentional hoặc health không là completed. Health rest pause toàn bộ nhắc
    vận động owner đến explicit resume; không cần thu thập chẩn đoán. Undo rest khôi
    phục trạng thái theo clock (planned hoặc missed), không tự bật notification.

## Native reminders

Chỉ tái dùng adapter/permission/cache/retry/cancellation; lịch cũ là hai giờ daily,
payload `check-in`. PR5 dùng registry persistent: unique `(owner, session, kind)`
→ integer notification ID cấp phát không trùng (không hash cắt ngắn đơn thuần),
desired revision/timezone/UTC/fire time. Payload opaque session ID + owner generation;
tap kiểm tra lại owner và current session, không mang thông tin sức khỏe.

Cancel khi complete/rest/cancel/logout/reschedule; reconcile sau resume/reboot/timezone
change và sau crash. Cancel lịch cũ trước bật lịch mới. Không schedule quá deadline;
quiet hours đẩy tới giờ hợp lệ chỉ nếu còn hữu ích. Một recovery prompt/episode và
tối đa một notification recovery/ngày; health pause ưu tiên cao nhất. OS inexact
delivery có thể muộn: tap luôn kiểm tra lại trạng thái. Init failure là degraded mode,
không chặn runApp. Các hành vi này cần test/device QA, chưa có trong source hiện tại.

## Migration và rollback

PR0 chỉ mô tả. PR1 có outbox/consent migration additive theo gate; PR2 nâng version
tiếp theo đã dùng, không cùng tranh một số version. Backup local trước migration,
transaction + integrity checks + migration ledger; reopen idempotent; mọi ID/owner/
createdAt/localDate/log count v2 giữ nguyên. Không tạo commitment lịch sử từ logs.
Metadata mới nullable/side-table, legacy row không cần backfill giả.

Rollback vận hành: tắt feature bằng build/config kiểm soát, giữ schema/data mới;
không drop table hoặc chạy app v2 cũ lên DB version cao hơn (sqflite có thể từ chối
downgrade). Cần compatibility build đọc v2 và bỏ qua tables mới. Restore backup
chỉ sau explicit consent vì có thể mất ghi mới; export delta trước. Cloud migrations
food/reminders hiện có không thay đổi. Mọi backend mới sau gate phải staging với
owner A/B/anon tests và migration order; source SQL không chứng minh đã deploy.
